# CLAUDE.md

Этот файл содержит инструкции для Claude Code (claude.ai/code) при работе с кодом этого репозитория.

## Команды

- `npm run dev` — запустить dev-сервер Vite с HMR
- `npm run build` — собрать production-версию в `dist/`
- `npm run preview` — запустить production-версию локально
- `npm test` — прогнать тесты (vitest, один прогон); `npm run test:watch` — в watch-режиме

Linter и formatter не настроены.

## Обязательное правило: контент-правила ответов

Длина вариантов ответа проверяется кодом — единый источник правды
`src/content-rules.js` (`validateAnswerText`, лимиты `MAX_ANSWER_*`). Им пользуются
и валидация в игре (`validateQuestions`, мягкое предупреждение), и тесты
(`tests/questions-answers.test.js` — жёсткий гейт по `public/questions.json`).

**При изменении лимитов меняй только `src/content-rules.js`** — и игра, и тесты
подхватят. После правок в `public/questions.json` прогоняй `npm test`: длинные
ответы (не влезающие в 2 строки) роняют data-тест.

Текущий лимит: **≤3 значимых слова** (служебные слова и местоимения не считаются),
≤44 символа, слово ≤18. Шрифт НЕ ужимается — не влезает, значит переформулировать.

## Обязательное правило: правки правил/промптов пайплайнов

**Любое изменение ПРАВИЛ или ПРОМПТОВ пайплайнов вопросов (генерация / судейство /
ревью / доводка) — сначала ПОКАЖИ предложением и применяй по аппруву, не коммить молча.**
Правило живёт прозой в нескольких местах — при изменении пройди ВСЕ зависимые точки по
**`docs/rules-map.md`** (карта связности), иначе пайплайн дрейфует (классика: поменял лимит
в `content-rules.js`, а промпт генератора остался со старым числом). Детерминированное
(длина, тире) проверяй КОДОМ, а не LLM.

## Обязательное правило: договорённости — в КОД, не в обещание

Любое согласованное поведение (фикс, правило пайплайна, изменение потока) **зашивай
СТРУКТУРНО — в код / тест / схему данных**, чтобы его нельзя было пропустить. Записка в
доке, память или «не забыть передать флаг» — это **НЕ фикс**: оно зависит от дисциплины и
тихо отваливается, а пользователь узнаёт постфактум после потраченных токенов. После фикса
**проверь, что он реально работает** (прогон/тест), а не заявляй «сделано». Если что-то по
объективным причинам остаётся только в доке и держится на дисциплине — **явно назови это**
(«напоминание, не enforce»), не выдавай за фикс. Новое поведение сверяй со старым на
дубли/конфликты (классика: фактчек добавили на генерации, но не выключили в полише — гонял
дважды). Эталон «как надо»: дубль фактчека убран флагом `factChecked` в данных + гейтом
`&& !it.factChecked` в полише, а не ручным `args.noWeb`.

## Архитектура

BigQuiz — это одностраничная викторина на **Phaser 4** с использованием **Vite**. Вся игра это один Phaser `GameScene` в `src/main.js` (~1000 строк); нет маршрутизатора, компонентного фреймворка или хранилища состояния. Всё рендерится на фикссированный холст 1120×640 (`Phaser.Scale.FIT`, по центру) в элемент `#app`.

UI рисуется императивно, а не декларативно. Нет DOM/HTML для контента игры — каждая панель, кнопка, чип и изображение это объект Phaser (`Graphics`/`Text`/`Image`), создаваемый в `create()` → `renderScreen()`. Ключевые последствия:

- `renderScreen()` это центральный ре-рендер: вызывает `this.children.removeAll()` для очистки холста, потом перестраивает все элементы с нуля для текущего вопроса. Большинство изменений состояния (новый вопрос, переключение звука) работают путём уничтожения и переrender, а не мутации на месте.
- Раскладка контролируется блоком констант позиций/размеров на уровне модуля (`MAIN_PANEL_*`, `CONTENT_X`, `STATS_X`, `AD_RAIL_X`, `IMAGE_*` и т.д.). Изменяйте эти константы, а не hard-codе координаты внутри методов render.
- Визуальный стиль находится в картах констант `COLORS` и `RADIUS`. Цвета хранятся как hex-числа Phaser (`0x...`); `colorToHex()` преобразует их в CSS-строки для стилей `Text`.
- Скруглённые прямоугольники это основной строительный блок — `createRoundedBox()` / `drawRoundedBox()` создают и перерисовывают их, `makeInteractiveBox()` добавляет hit-области. Состояния hover/click обрабатываются перерисовкой одного объекта graphics с другим заполнением.

### Данные вопросов и поток

- Вопросы загружаются во время выполнения из **`public/questions.json`** (как `/questions.json`), а не из бандла. Схема вопроса: `id`, `question`, `answers` (ровно 4), `correctAnswerIndex` (0–3), `categories` (1–3), `image`, `imageRole`, `requiresImage` (boolean). `validateQuestions()` проверяет это при загрузке и показывает русское сообщение об ошибке если невалидно.
- **Прод / пул ревью (ВАЖНО):** `public/questions.json` — это ПРОД, только вопросы со статусом `approved`; их одних показывает игра (`getRandomQuestion` фильтрует по `reviewStatus === 'approved'`). Всё, что на ревью (генерации, доработки), лежит в **`data/review-pool.json`** (ПУЛ, вне `public/`, в zip не попадает). Статусы: `pending`/`approved`/`rework`/`discard`. Не клади неотревьюенные вопросы прямо в прод — они попадут в игру. Полный замкнутый цикл (генерация → судья → ревью в `admin.html` → доработка через `polish` → анализатор пишет примеры/предложения) описан в **`docs/review-runbook.md`** и разделе 4a `docs/GDD_LITE.md`. Операции прод/пул — `scripts/lib/review-store.mjs`.
- `getRandomQuestion()` циклирует через approved-вопросы без повторений (отслеживая `shownQuestionIds`) перед перемешиванием, и избегает показа одного вопроса дважды подряд.
- **Правила показа карточки — единый модуль `src/card-rules.js`** (чистый, без Phaser/DOM): его импортируют и игра (`src/main.js`), и админка-препрод (`src/admin/admin.js`), чтобы превью в админке точь-в-точь совпадало с продом. Любое новое правило отображения (порядок ответов, выбор картинки и т.п.) добавляй СЮДА. Сейчас там: `orderAnswers` (числовой набор ответов → по убыванию значения, нечисловой → как есть) и `imageCandidatePaths` (.webp первым).
- Порядок ответов: числовые наборы показываются по убыванию (детерминированно, правило `card-rules`), нечисловые перемешиваются при каждом render (`prepareShuffledAnswers()` → анти-чит позиции). Поэтому `currentCorrectAnswerIndex` (после показа) отличается от `correctAnswerIndex` вопроса (оригинальный).
- Изображения загружаются вручную через browser `Image()` API (не через loader Phaser), чтобы можно было пробовать несколько расширений файлов по очереди — см. `getImageCandidatePaths()` (пробует `.webp` первым, затем `.jpg/.jpeg/.png/.gif`). `.webp` первый, потому что build-конвейер (`scripts/optimize-images.js`) всегда приводит картинки к webp, а расширение в `questions.json` может быть устаревшим. Загруженные изображения регистрируются как Phaser-текстуры с ключом `question_image_<id>`. Если `requiresImage` true и загрузка не удалась, вопрос пропускается; иначе показывается placeholder. Готовые `.webp` лежат в `public/assets/images/` (попадают в архив игры), оригиналы-исходники — в `scripts/images-raw/` (вне сборки). Подбор/оптимизация: `scripts/fetch-images.js` (скачивает с Wikipedia/Commons + сразу оптимизирует) и `scripts/optimize-images.js` (WebP ≤768px, q82); npm-скрипты `images` / `optimize:images`.
- Mock-реклама появляется каждые `ANSWERS_BEFORE_AD` (5) ответов (`shouldShowAd()` / `showMockAd()`).

### Аналитика

Все события игры логируются через `logEvent(name, payload)`, которая только `console.log`ит структурированный объект `[BigQuiz event]` (с `sessionId` и ISO-временем). Нет backend — это поверхность инструментации, которую можно расширить если добавится реальная телеметрия.

### Шрифты и локализация

Шрифт `Roboto` хостится локально в `public/fonts/` через `@font-face` в `src/style.css`. Весь UI-текст на русском.

## Обязательное правило: актуализация категорий

**После каждого изменения в `public/categories.json` — обновляй `docs/categories.md`:**

1. Синхронизируй дерево категорий (добавленные / удалённые / переименованные категории и подкатегории).
2. Обнови номер версии в заголовке (v2 → v3 и т.д.).

## Обязательное правило: актуализация GDD

**После каждого изменения в коде, которое затрагивает игровые механики, UI, поток данных или архитектуру — обновляй `docs/GDD_LITE.md`:**

1. Обнови затронутые разделы (механика, экраны, схемы данных).
2. Увеличь номер версии (v0.8 → v0.9 и т.д.).
3. Добавь строку в таблицу версионирования с датой и описанием изменений.
4. Если фича реализована частично (мёртвый код, заглушка) — отметь «Статус: в разработке» прямо в разделе GDD.

Не нужно обновлять GDD при: рефакторинге без изменения поведения, исправлении багов без изменения спецификации, изменениях констант позиционирования.

## Обязательное правило: документация Яндекс.Игр

**Когда вопрос касается ограничений платформы Яндекс.Игры, требований к игре, правил публикации или модерации, SDK и т.п. — сначала ищи ответ в папке `docs/`, а не в интернете.** Там лежит вся официальная документация платформы Яндекс.Игры, выкачанная заранее.

Только если в `docs/` нужного ответа нет — тогда обращайся к интернету.
