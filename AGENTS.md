# AGENTS.md

Правила для Codex и других агентных инструментов при работе с этим репозиторием.

## Команды

- `npm run dev` — запустить dev-сервер Vite с HMR.
- `npm run build` — собрать production-версию в `dist/`.
- `npm run preview` — запустить production-версию локально.
- `npm test` — прогнать тесты Vitest одним прогоном.
- `npm run test:watch` — тесты в watch-режиме.
- `npm run lint` — ESLint.

## Контент-правила ответов

Длина вариантов ответа проверяется кодом. Единый источник правды:
`src/content-rules.js` (`validateAnswerText`, лимиты `MAX_ANSWER_*`).

Эти правила используют:

- валидация в игре: `validateQuestions` в `src/main.js` как мягкое предупреждение;
- тесты: `tests/questions-answers.test.js` как жёсткий гейт по `public/questions.json`.

При изменении лимитов меняй только `src/content-rules.js`; игра и тесты должны подхватить правило автоматически. После правок в `public/questions.json` прогоняй `npm test`.

Текущий лимит: ≤3 значимых слова, ≤44 символа, слово ≤18. Служебные слова и местоимения не считаются. Шрифт ответов не ужимается: если текст не влезает, ответ нужно переформулировать.

## Правки правил и промптов пайплайнов

Любое изменение правил или промптов пайплайнов вопросов: генерация, судейство, ревью, доводка — сначала показать предложением и применять только после аппрува. Не коммитить такие изменения молча.

При изменении правил пройти все зависимые точки по `docs/rules-map.md`, чтобы пайплайн не разъехался. Детерминированные проверки, например длина ответов и тире, должны проверяться кодом, а не LLM.

## Договорённости фиксировать структурно

Любое согласованное поведение нужно зашивать в код, тест, схему данных или другой enforceable-механизм. Документ, память или устное обещание — это напоминание, не фикс.

После правки обязательно проверить, что поведение реально работает. Если что-то объективно остаётся только в документации и держится на дисциплине, явно назвать это как не-enforced правило.

Новое поведение сверять со старым на дубли и конфликты.

## Архитектура

BigQuiz — одностраничная викторина на Phaser 4 и Vite. Игра рендерится в одном Phaser `GameScene` в `src/main.js`. Нет роутера, компонентного фреймворка или внешнего хранилища состояния.

Вся игровая UI-разметка рисуется императивно в canvas объектами Phaser (`Graphics`, `Text`, `Image`). DOM/HTML для контента игры не используется.

Ключевые правила работы с архитектурой:

- `renderScreen()` — центральный re-render: очищает сцену и перестраивает элементы для текущего вопроса.
- Позиции, размеры и визуальные токены держать в константах верхнего уровня, а не размазывать hard-code по render-методам.
- Цвета Phaser хранятся как hex-числа `0x...`; для текста использовать `colorToHex()`.
- Скруглённые прямоугольники строятся через `createRoundedBox()` / `drawRoundedBox()`, интерактивные зоны — через `makeInteractiveBox()`.
- Состояния hover/click обычно делаются перерисовкой существующего `Graphics`.
- Сохранять существующую архитектуру и делать минимально достаточные изменения.

## Данные вопросов и поток

- Вопросы загружаются runtime из `public/questions.json` как `/questions.json`, а не из бандла.
- `public/questions.json` — прод. В игре должны быть только `approved` вопросы.
- Ревью-пул живёт в `data/review-pool.json` и не попадает в zip игры.
- Статусы ревью: `pending`, `approved`, `rework`, `discard`.
- Операции прод/пул находятся в `scripts/lib/review-store.mjs`.
- Цикл генерации, судейства, ревью и доводки описан в `docs/review-runbook.md` и разделе 4a `docs/GDD_LITE.md`.
- Не класть неотревьюенные вопросы напрямую в `public/questions.json`.

Правила карточки:

- Единый модуль отображения карточки — `src/card-rules.js`.
- Его импортируют игра и админка-препрод, чтобы превью совпадало с продом.
- Любое новое правило отображения карточки, порядка ответов или выбора картинки добавлять туда.
- Числовые наборы ответов показываются по убыванию значения.
- Нечисловые ответы перемешиваются при render.
- `currentCorrectAnswerIndex` после показа может отличаться от исходного `correctAnswerIndex`.

Изображения:

- Готовые `.webp` лежат в `public/assets/images/`.
- Оригиналы лежат вне сборки в `scripts/images-raw/`.
- Подбор и оптимизация: `scripts/fetch-images.js`, `scripts/optimize-images.js`, `npm run images`, `npm run optimize:images`.
- `imageCandidatePaths()` пробует `.webp` первым.

## Аналитика, шрифты, локализация

- События логируются через `logEvent(name, payload)` в `console.log` структурированным объектом `[BigQuiz event]`.
- Backend-телеметрии нет.
- Шрифт `Roboto` локально в `public/fonts/`, подключён через `src/style.css`.
- UI-текст на русском.

## Обязательное правило: актуализация категорий

**После каждого изменения в `public/categories.json` — обновляй `docs/categories.md`:**

1. Синхронизируй дерево категорий (добавленные / удалённые / переименованные категории и подкатегории).
2. Обнови номер версии в заголовке (v2 → v3 и т.д.).

## Обязательное правило: актуализация GDD

**После каждого изменения в коде, которое затрагивает игровые механики, UI, поток данных или архитектуру — обновляй `docs/GDD_LITE.md`:**

1. Обнови затронутые разделы (механика, экраны, схемы данных).
2. Увеличь номер версии (v0.8 → v0.9 и т.д.).
3. Добавь строку в таблицу версионирования с датой и описанием изменений.
4. Если фича реализована частично (мёртвый код, заглушка) — отметь «Статус: в разработке» прямо в разделе GDD.

Не нужно обновлять GDD при: рефакторинге без изменения поведения, исправлении багов без изменения спецификации, изменениях констант позиционирования.

## Обязательное правило: актуализация UI-документа

**После каждого изменения дизайна, UI или UX игрового экрана — обновляй `docs/ui-design-system.md`.**

1. Используй `docs/ui-design-system.md` как источник правды перед любыми визуальными правками.
2. Если пользователь просит изменить стиль, компоновку, размеры, состояния, анимации или поведение UI — сначала сверяйся с этим документом.
3. После реализации обнови документ под фактическое состояние интерфейса в том же наборе правок.
4. Если правка меняет не только внешний вид, но и специфику экрана/режима, дополнительно обнови `docs/GDD_LITE.md`.

## Обязательное правило: документация Яндекс.Игр

**Когда вопрос касается ограничений платформы Яндекс.Игры, требований к игре, правил публикации или модерации, SDK и т.п. — сначала ищи ответ в папке `docs/`, а не в интернете.** Там лежит вся официальная документация платформы Яндекс.Игры, выкачанная заранее.

Только если в `docs/` нужного ответа нет — тогда обращайся к интернету.

## Engineering Behavior

Эти правила снижают типичные ошибки LLM при кодинге. Для тривиальных задач применяй здравый смысл, но по умолчанию выбирай осторожность и проверяемость.

### Думай перед кодом

- Не делай скрытых предположений. Коротко называй рабочие assumptions, если они влияют на решение.
- Если есть несколько разумных трактовок задачи — покажи варианты, не выбирай молча.
- Если требование неясно и разумная догадка рискованна — остановись, назови что именно неясно, задай вопрос.
- Если есть более простой подход — скажи об этом. Возражай против лишней сложности, когда это оправдано.
- Не раскрывай длинную цепочку рассуждений; показывай только выводы, план, assumptions, tradeoffs и результат.

### Простота прежде всего

- Пиши минимальный код, который решает поставленную задачу.
- Не добавляй функции, гибкость, конфиги или расширяемость, которые не просили.
- Не создавай абстракции для одноразового кода.
- Не добавляй обработку сценариев, которые в текущей архитектуре невозможны.
- Если решение выглядит так, будто 200 строк можно заменить 50 без потери ясности, упрощай.

### Хирургические изменения

- Трогай только то, что нужно для запроса пользователя.
- Не улучшай соседний код, комментарии, форматирование или архитектуру заодно.
- Не рефактори несломанное.
- Совпадай с существующим стилем проекта, даже если выбрал бы другой стиль в новом коде.
- Если видишь unrelated dead code — упомяни, но не удаляй без запроса.
- Удаляй только те unused imports/variables/functions, которые появились из-за твоих изменений.
- Каждая изменённая строка должна напрямую прослеживаться к запросу пользователя.

### Цель и верификация

- Превращай задачу в проверяемую цель.
- Для багфикса по возможности сначала воспроизведи проблему тестом или явной проверкой, затем исправляй.
- Для refactor-задач проверяй, что поведение не изменилось.
- Для нетривиальных задач давай короткий план формата: шаг → проверка.
- После реализации запускай релевантные проверки: тесты, build, lint, smoke-check или ручную проверку через dev server.
- Не объявляй задачу завершённой, пока результат не проверен или пока явно не назван блокер.

## Режим работы: Full Focus

Выполняй задачи в режиме гиперфокуса на результат.

Do not explain your reasoning.
Do not provide educational content.
Do not brainstorm.

**Read. Analyze. Plan. Execute. Verify.**

Continue working until the task is completely finished or blocked by missing information.

### Rules:

1. Output only actions, code, analysis, plans, fixes, and results.
2. Never produce motivational text, filler, apologies, or explanations unless explicitly requested.
3. Before coding:
   - Analyze the repository structure.
   - Identify relevant files.
   - Build a mental model of dependencies.
   - Create a concise execution plan.

4. For every task:
   - Think step-by-step internally.
   - Search the codebase aggressively.
   - Read before editing.
   - Prefer understanding over assumptions.

5. When implementing:
   - Make the smallest correct change.
   - Preserve existing architecture.
   - Avoid unnecessary refactoring.
   - Keep style consistent with the repository.

6. After implementation:
   - Run relevant tests.
   - Check for regressions.
   - Verify imports, types, linting, and edge cases.
   - Report only actionable findings.

7. If requirements are ambiguous:
   - Do not guess.
   - List exactly what information is missing.
   - Propose the most likely interpretations.

8. Work in a continuous execution loop:

   OBSERVE → ANALYZE → PLAN → EXECUTE → VERIFY → IMPROVE

9. Maintain a task list at all times:
   - Completed
   - In Progress
   - Next

10. Optimize for:
   - correctness
   - speed
   - reliability
   - maintainability

Act like a senior engineer responsible for a production system with 10 million users.
